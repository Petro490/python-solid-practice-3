# Практическая работа №3: ООП в Python (SOLID)

Домашнее задание выполнено по пяти принципам SOLID. Каждая задача — отдельный
модуль, который можно запустить самостоятельно, и всё вместе запускается
через `main.py`.

## Как запустить

```bash
python main.py        # все задачи
python main.py 3      # только задача 3
python task3_lsp.py   # отдельный файл задачи
```

Требуется Python 3.8+ (проверено на 3.13). Внешних библиотек нет — только
стандартная библиотека (`abc`, `urllib`).

## Файлы

## Что сделано по задачам

### Задача 1. SRP — `task1_srp.py`

**Нарушение в исходном коде:** класс `Journal` одновременно управлял записями,
писал/читал файлы и содержал метод для загрузки из сети. Три разные причины
для изменения в одном классе.

**Решение:**

- `Journal` — только записи: `add_entry`, `remove_entry`, `find`, `clear`,
  `__str__`, `__len__`, свойства `entries` и `count`. Список записей закрыт,
  снаружи меняется только методами; счётчик не сбрасывается при удалении,
  поэтому номера не повторяются.
- `JournalPersistence` — только ввод-вывод: статические `save`, `load`,
  `load_from_web` (статические, потому что состояние не нужно — журнал
  передаётся параметром).
- `Journal.replace_entries()` позволяет восстановить журнал из внешнего
  источника, при этом `Journal` не знает, откуда пришли данные.
- При загрузке счётчик восстанавливается по номерам строк вида `3: текст`,
  поэтому нумерация продолжается корректно.
- Проверка расширяемости: `JournalEmailSender` добавляет отправку по email
  без единой правки `Journal` и `JournalPersistence`.

Файл, сохранённый в демонстрации (`journal_demo.txt`), удаляется автоматически.

### Задача 2. OCP — `task2_ocp.py`

**Нарушение:** `DiscountCalculator.calculate_discount` перебирал
`customer.type` через `if/elif`; новый тип клиента требовал правки метода.

**Решение:**

- абстрактный `Customer` с методом `calculate_discount(order_total)` и общей
  логикой `total_with_discount`;
- `NewCustomer` (2%), `RegularCustomer` (5%), `VIPCustomer` (15%) —
  переопределяют формулу, ставка вынесена в атрибут `discount_rate`;
- `DiscountCalculator` работает только с абстракцией: `if/elif` и проверок
  типа больше нет, вызывается полиморфный метод клиента;
- `PremiumCustomer` (25%) добавлен новым классом — существующий код не
  менялся, что и доказывает соответствие OCP.

Демонстрация выводит таблицу: клиент, процент скидки, сумма скидки, итог.

### Задача 3. LSP — `task3_lsp.py`

**Нарушение:** `Square(Rectangle)` переопределял `set_width`/`set_height` так,
что менялись оба размера. Функция, рассчитанная на прямоугольник (ширина 5,
высота 4 → площадь 20), для квадрата давала 16 — контракт базового класса
нарушался.

**Решение:**

- абстрактный `Shape` с методом `area()`;
- `Rectangle` и `Square` — независимые наследники `Shape`, друг от друга не
  наследуются, поэтому «квадратных» сюрпризов у прямоугольника нет;
- размеры задаются через `property`-сеттеры: проверка «больше нуля» работает
  при любом способе изменения и для всех фигур;
- `print_area(shape)` принимает любую `Shape`;
- `test_lsp()` — тестовая функция с `assert`: проверяет площади, изменение
  размеров и отказ при отрицательной стороне.

### Задача 4. ISP — `task4_isp.py`

**Нарушение:** `MultiFunctionDevice` требовал от наследников четыре метода;
`SimplePrinter` вынужденно реализовывал три метода заглушками
`NotImplementedError`.

**Решение:**

- четыре узких интерфейса: `Printable`, `Scannable`, `Faxable`, `Copyable`;
- `SimplePrinter` реализует только `Printable`, `OfficePrinter` —
  `Printable + Scannable + Copyable` (без факса), `AllInOnePrinter` — все
  четыре;
- клиентские функции (`print_anything`, `scan_anything`) зависят от узких
  интерфейсов и проверяют поддержку через `isinstance`;
- демонстрация показывает набор возможностей каждого устройства и что у
  `SimplePrinter` нет методов сканирования/факса/копирования вообще, а не
  заглушек.

### Задача 5. DIP — `task5_dip.py`

**Нарушение:** `NotificationService` сам создавал `EmailSender` и `SMSSender`
и выбирал канал через `if/elif`, то есть зависел от конкретных реализаций.

**Решение:**

- абстракция `Notifier` с методом `notify(user, message)`;
- реализации `EmailNotifier`, `SMSNotifier`, `PushNotifier`, а также
  `ConsoleNotifier` (заглушка для тестов) и `MultiNotifier` (рассылка сразу в
  несколько каналов);
- `NotificationService` принимает `Notifier` в конструкторе (внедрение
  зависимости) и проверяет контракт через `isinstance`;
- какой контакт пользователя нужен (email, телефон, имя), знает сам канал, а
  не сервис: поэтому новый канал не требует правок `NotificationService`;
- новый канал `PushNotifier` и композитный `MultiNotifier` работают без
  изменения сервиса;
- `ConsoleNotifier` показывает, как подменить реальную отправку в тестах.

## Итог

Во всех пяти задачах устранены исходные нарушения: обязанности разделены,
расширение выполняется добавлением классов, а не правкой существующего кода,
наследование не ломает контракты базовых классов, интерфейсы узкие, а
высокоуровневые модули зависят от абстракций. Код снабжён комментариями,
объясняющими, что и почему изменено.
